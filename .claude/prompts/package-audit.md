# 상용 출시 감사 프롬프트

에디터 도구·라이브러리 패키지를 **돈을 받고 팔 수 있는 상태인가**의 관점에서 뜯는 프롬프트입니다.
일반 코드리뷰가 아닙니다 — "잘 짜였는가"가 아니라 **"환불 사유가 무엇인가"** 를 찾습니다.

## 쓰는 법

아래 `▼ 프롬프트` 이하를 그대로 붙여 넣고, 대괄호 세 곳만 채웁니다.
`[대상]` 은 경로나 "현재 저장소", `[채널]` 은 Asset Store / 직접 판매 / 사내 배포 중 하나,
`[깊이]` 는 `빠르게`(반나절) 또는 `전면`(며칠) 입니다.

---

## ▼ 프롬프트

[대상] 을 **[채널] 로 유료 출시한다는 전제**로 감사하십시오. 깊이는 [깊이] 입니다.

### 당신의 입장

이 코드를 쓴 사람은 실력이 있습니다. 표면적인 칭찬과 일반론은 아무 값이 없습니다.
당신은 **환불을 요구할 첫 구매자**이자, 그 환불을 미리 막으려는 검토자입니다.
"이 정도면 괜찮다"는 결론이 나온다면, 충분히 파고들지 않은 것입니다.

동시에 **없는 문제를 만들지 마십시오.** 지어낸 결함 하나가 진짜 결함 열 개의 신뢰를 깎습니다.
확신이 없으면 "확인 필요"라고 적고 무엇을 어떻게 확인해야 하는지 쓰십시오.

### 근거 표기 — 모든 항목에 붙일 것

| 표기 | 뜻 |
|---|---|
| `측정` | 이 저장소에서 실제로 돌려 보거나 세어 본 것 |
| `코드` | 코드를 읽고 확정한 것 (경로:줄 을 반드시 함께) |
| `추정` | 코드에서 추론했으나 실행으로 확인하지 못한 것 |
| `인용` | 플랫폼 공식 문서·약관에서 확인한 것 |

`추정` 은 그렇게 적으십시오. 측정하지 않은 성능 수치를 단정하지 마십시오.

### 반드시 먼저 할 일

1. **문서가 주장하는 것과 코드가 하는 것을 대조하십시오.** README·주석·CHANGELOG 가
   "우리는 X 를 하지 않는다"고 선언한 자리를 모아, 코드가 정말 그런지 하나씩 확인합니다.
   **가장 큰 결함은 거의 항상 여기서 나옵니다** — 저자가 그 자리를 이미 중요하다고 알고 있고,
   그래서 적어 뒀고, 그런데도 구현이 어긋나 있으면 아무도 의심하지 않기 때문입니다.
2. **빌드하고 검사를 실제로 돌리십시오.** 돌릴 수단이 있으면 반드시 돌립니다.
   (Unity 라면 배치 모드, `-runTests`) 못 돌렸으면 **못 돌렸다고 결론에 쓰십시오.**
3. **작업 트리 상태를 확인하십시오.** 컴파일되지 않거나 편집 중이면 그 사실을 먼저 보고합니다.
4. **패키지 메타데이터를 읽으십시오.** 버전·라이선스·의존성·최소 플랫폼 판·URL 이 실제와 맞는지.
   저장소 공개 여부처럼 **밖에서 확인할 수 있는 사실은 추측하지 말고 확인하십시오.**

### 무엇을 찾는가 — 우선순위 순

**1순위 · 조용한 데이터 손실.** 오류도 경고도 없이 사용자의 값이 바뀌거나 사라지는 자리.
이것이 유료 도구를 죽입니다. 특히 이런 모양을 찾으십시오.

- 값을 **보고** 타입·의미를 추론하는 자리 (`007`→`7`, `1.10`→`1.1`, 긴 숫자→지수 표기)
- 인코딩·로케일·개행·경로 구분자를 가정하는 자리 — **기계마다 결과가 갈리는가**
- 덮어쓰기·삭제 전에 무엇을 확인하는가. 그 확인이 **놓치는 경우**는 무엇인가
- 실패했는데 호출부가 그것을 알 수 없는 자리 (`null` 반환, 삼켜진 예외, 관측되지 않는 Task)
- 왕복(export→import)이 원본과 달라지는 자리. **스스로 번지는가**

**2순위 · 상품으로서의 결격.** 코드가 아니라 파는 물건의 문제.

- 라이선스와 유통 경로가 서로 모순되지 않는가 (무료로 받을 길이 상품 페이지에 적혀 있지 않은가)
- 배포본에 **들어가면 안 되는 것**이 들어가는가 (내부 검토 문서, 경쟁 분석, 자기 약점 목록, 키, 개인 연락처)
- 배포본에서 **빠지는 것**은 없는가 (문서·샘플이 배포 형태에서 사라지는가)
- 버전·지원 채널·업그레이드 안내가 유료 제품의 꼴을 갖췄는가
- 대상 시장의 언어로 되어 있는가. **반쯤 번역된 상태가 아닌가** (그쪽이 더 나쁩니다)

**3순위 · 처음 30분에 막히는 자리.** 구매자가 가장 먼저 하는 일부터 따라가 보십시오.

- 샘플·튜토리얼이 **존재하는** 메뉴·API 를 가리키는가 (실제 선언과 문서를 기계적으로 대조)
- 흔한 프로젝트 구성(모듈 분리, 빌드 설정, 대소문자 구분 파일시스템)에서 그대로 되는가
- 첫 오류 메시지가 **무엇을 고쳐야 하는지** 말하는가

**4순위 · 규모에서 무너지는 자리.**

- 입력 크기에 비례하는 작업이 진행 표시·취소 없이 도는가
- 프로젝트 전체를 훑는 일이 얼마나 자주 일어나는가. 캐시가 언제 버려지는가
- 자료 구조가 O(n×m) 인 자리. n·m 이 현실에서 얼마인가

**5순위 · 검사되지 않은 자리.** 검사 수를 세지 말고 **무엇이 덮이지 않았는지** 보십시오.
네트워크·인증·플랫폼 API·에러 경로가 비어 있는 경우가 많고, 유료 차별화 기능이 하필 거기 있습니다.

### 결과물의 모양

1. **한 줄 결론** — 출시를 막는 것이 무엇인가. 에두르지 마십시오.
2. **막는 것(Blocker)** — 순위대로. 각 항목에:
   - 무엇이 잘못됐는지 한 문장
   - **재현**: 구체적 입력 → 구체적으로 잘못된 결과 (`이 값이 이렇게 됩니다` 표가 좋습니다)
   - `파일:줄` 링크
   - 고치는 방향 한두 줄 (전체 설계 갈아엎기 말고, 실제로 할 수 있는 것)
3. **잘하고 있는 것** — 짧게, 그러나 반드시. 근거와 함께.
   비판만 있는 감사는 무엇을 지켜야 할지 알려 주지 않습니다.
4. **사람이 정해야 할 것** — 당신이 정할 수 없는 갈림길과, 각각의 대가.
5. **하는 순서** — 단계로 묶고, 각 단계가 무엇을 해금하는지 적으십시오.

### 하지 말 것

- 일반론 (`테스트를 더 짜세요`, `문서화가 필요합니다`) — 이미 아는 말은 지면 낭비입니다
- README 를 요약해 되돌려 주기 — 저자가 쓴 글입니다
- 스타일·명명·포매팅 지적을 결함 목록에 섞기 — 별도로 묶거나 빼십시오
- 채널이 요구하지 않는 요건을 지어내기 — 요건을 말할 땐 출처를 다십시오
- 확인할 수 있는 사실을 추측하기 (저장소 공개 여부, 라이브러리 존재, API 시그니처)
- 발견을 부풀리기. 사소한 것은 사소하다고 적으십시오

### 마지막

감사가 끝나면 스스로에게 물으십시오 — **"이 도구를 산 사람이 첫 주에 겪을 최악의 일은 무엇인가?"**
그 답이 1순위 목록의 맨 위에 없다면, 목록이 틀린 것입니다.
